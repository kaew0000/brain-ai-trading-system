# Snapshot Format — Phase W4

Six files, all under `world/data/runtime/`, all written only by
`RuntimeManager` (`world/runtime/runtime_manager.py`). Each validates
against a schema in `world/data/schemas/`; `world/tests/
test_runtime_schema.py` enforces this on every test run.

| File | Schema | Origin |
|---|---|---|
| `world.json` | `world.schema.json` | Phase W1 schema, extended in W4 with an optional `activeAgents` field |
| `events.json` | `events.schema.json` | Phase W1 schema, reused as-is |
| `missions.json` | `missions.schema.json` | Phase W1 schema, reused as-is |
| `notifications.json` | `notifications.schema.json` | Phase W1 schema, reused as-is — content *derived* from events, no dedicated reader |
| `portfolio.json` | `portfolio.schema.json` | New in Phase W4 |
| `telemetry.json` | `telemetry.schema.json` | New in Phase W4 |

**Why four of six reuse Phase W1 schemas:** `world/data/schemas/`
already had `world.schema.json`, `events.schema.json`,
`missions.schema.json`, and `notifications.schema.json` from Phase W1
(design-only placeholders, already had samples, already schema-valid)
that matched what Phase W4 needed almost exactly. Creating a second,
`runtime_`-prefixed set of near-duplicate schemas would have been
exactly the kind of parallel implementation this project's engineering
rules forbid — extending the existing ones was the correct move. See
Patch Notes for the one field this required adding.

## `world.json`

```json
{
  "version": "0.1.0",
  "timestamp": "<ISO-8601>",
  "engineStatus": "idle | active | recovering | halted",
  "activeDistricts": ["<district id>", "..."],
  "activeAgents": ["<agent ref>", "..."]
}
```

`engineStatus` is `"active"` only if at least one of the five readers
actually returned data this capture (`EngineSnapshot.sources_available`);
otherwise `"idle"`. `activeDistricts`/`activeAgents` are derived by
`SnapshotBuilder.build_world` from the districts/agents mentioned in
that capture's events, missions, and portfolio positions.

## `events.json` / `missions.json`

Straight pass-through of `EventReader`/`MissionReader` output,
reshaped to each schema's exact field names. See
`world/data/schemas/events.schema.json` /
`missions.schema.json` for the full shape (both predate Phase W4).

## `notifications.json`

**Derived, not read.** Every event with `severity` of `warning` or
`critical` becomes one notification (`id` prefixed `notif-from-`,
`read: false`). No `notification_reader.py` exists — the Phase W4
task's reader list only names five readers.

## `portfolio.json`

```json
{
  "timestamp": "<ISO-8601>",
  "totalPositions": 0,
  "positions": [
    { "symbol": "BTCUSDT", "district": "portfolio-garden", "sizeLabel": "medium" }
  ]
}
```

`sizeLabel` is a free-text display label (e.g. `"small"`/`"medium"`/
`"large"`), deliberately not a raw notional amount — this file is a
presentation-only reflection for the World, not a financial data feed.

## `telemetry.json`

```json
{
  "timestamp": "<ISO-8601>",
  "metrics": [
    { "name": "adapter_lag_seconds", "value": 0.0, "unit": "seconds", "district": "data-center" }
  ]
}
```

## Current checked-in state

All six files are honestly empty/idle placeholders — generated by
actually running `RuntimeManager.run_once()` with zero readers wired
(not hand-written), so they're guaranteed schema-valid and consistent
with what the real pipeline produces when no source is connected yet.
